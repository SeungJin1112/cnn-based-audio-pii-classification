## 총평

제3자 입장에서 보면, **실험 계획 자체는 구현 가능한 수준으로 잘 정리되어 있지만, 현재 설계 그대로라면 결론의 해석력이 상당히 약합니다.**

특히 핵심 문제는 이것입니다.

> 지금 모델이 잘 맞히더라도, 그것이 “PII 포함 여부를 오디오에서 감지했다”는 증거라기보다
> **“전화번호 낭독 특유의 길이·리듬·숫자 나열 패턴을 감지했다”는 증거일 가능성이 훨씬 큽니다.**

따라서 현재 plan.md는 **개발 계획서로는 괜찮지만, 실험 설계서로는 confound 통제가 부족**합니다.

---

# 1. 가장 큰 문제: 양성/음성 데이터가 너무 다름

현재 데이터 구조는 다음과 같습니다.

| 클래스      |      내용 |  평균 길이 | 발화 스타일     |
| -------- | ------: | -----: | ---------- |
| Positive | 전화번호 포함 | 약 6.7초 | 숫자 또박또박 나열 |
| Negative |   일반 문장 | 약 4.5초 | 자연 문장      |

이러면 CNN이 배울 수 있는 단서가 너무 많습니다.

모델은 PII를 이해하지 않아도 됩니다. 그냥 아래만 배워도 분류가 됩니다.

* 음성이 긴가?
* 숫자가 연속적으로 나열되는 리듬인가?
* 침묵 간격이 규칙적인가?
* 음절 길이가 일정한가?
* 마지막 부분에 긴 패딩이 적은가?
* positive 쪽 TTS 스타일과 negative 쪽 TTS 스타일이 다른가?

즉, **PII detection이 아니라 dataset artifact detection**이 될 위험이 큽니다.

현재 문서에도 이 한계를 인지하고 있다고 쓰여 있지만, “주의사항”으로 쓰는 것만으로는 부족합니다. 이 한계는 부가적 문제가 아니라 **실험 결론의 중심을 흔드는 핵심 위협**입니다.

---

# 2. “우연 수준 이상이면 작동한다”는 기준이 약함

현재 1차 기준은 다음에 가깝습니다.

> F1이 우연 수준보다 안정적으로 높으면 접근 가능성을 보인다.

이 기준은 너무 낮습니다.

왜냐하면 현재 데이터에서는 **duration-only baseline**만으로도 우연 수준을 넘을 가능성이 있습니다.

예를 들어 모델이 아래 규칙만 써도 꽤 맞힐 수 있습니다.

```text
길이가 5.5초 이상이면 Positive
그보다 짧으면 Negative
```

이런 상황에서 CNN이 F1 0.85를 찍어도, 그것은 CNN이 멜 스펙트로그램에서 PII 패턴을 학습했다는 증거가 아닙니다.

따라서 최소한 아래 baseline이 필요합니다.

| Baseline                                         | 목적                                                     |
| ------------------------------------------------ | ------------------------------------------------------ |
| Majority baseline                                | 클래스 균형 확인용. 현재는 50%                                    |
| Duration-only logistic regression                | 길이 단서만으로 분류 가능한지 확인                                    |
| Simple acoustic feature baseline                 | RMS, zero-crossing, spectral centroid, duration 등으로 분류 |
| Random forest / logistic on handcrafted features | CNN이 정말 스펙트로그램 패턴을 배웠는지 비교                             |

이 baseline들을 이기지 못하면, CNN 실험은 설득력이 크게 떨어집니다.

---

# 3. Stratified random split만으로는 부족함

현재 split은 `train/val/test = 70/15/15 stratified`입니다.

이것도 위험합니다.

만약 데이터가 템플릿 기반 생성이라면, train과 test에 비슷한 문장 구조가 섞일 수 있습니다. 그러면 모델은 일반화가 아니라 **템플릿/화자/생성 패턴 암기**를 할 수 있습니다.

특히 TTS 기반 데이터라면 다음 기준을 고려해야 합니다.

## 권장 split

| Split 기준                | 필요성                                     |
| ----------------------- | --------------------------------------- |
| Speaker-disjoint split  | 같은 TTS 화자/목소리가 train과 test에 동시에 들어가지 않게 |
| Template-disjoint split | 같은 문장 템플릿이 train/test에 섞이지 않게           |
| Length-stratified split | positive/negative 길이 분포 차이 최소화          |
| Seed 고정                 | 재현성 확보                                  |

현재 계획에는 stratified만 있고, **speaker-disjoint / template-disjoint에 대한 언급이 없습니다.**
이건 논문/보고서 관점에서는 꽤 큰 약점입니다.

---

# 4. Padding이 길이 정보를 그대로 노출할 가능성

전처리에서 8초 기준 pad/truncate를 사용한다고 되어 있습니다.

문제는 positive 평균이 6.7초, negative 평균이 4.5초라는 점입니다.

그러면 negative는 뒤쪽에 padding 영역이 훨씬 많이 생깁니다. CNN은 멜 패턴을 볼 필요 없이 **검은 영역/무음 영역의 길이**만 보고도 분류할 수 있습니다.

이건 매우 치명적인 leakage입니다.

## 보완책

* 모든 샘플을 무작위 crop으로 동일 길이 segment화
* padding mask를 쓰거나, padding 영역을 랜덤 노이즈/배경음으로 채움
* duration-matched subset을 따로 만들어 평가
* positive/negative 모두 동일 길이로 강제 생성
* E2E 평가와 별도로 “길이 통제 평가셋”을 둠

최소한 결과표에는 다음을 분리해야 합니다.

| 평가셋                                | 의미                    |
| ---------------------------------- | --------------------- |
| Original test                      | 현재 데이터 조건에서 성능        |
| Length-matched test                | 길이 단서 제거 후 성능         |
| Number-negative test               | 일반 숫자 나열 음성에 대한 오탐 확인 |
| Korean-pronunciation positive test | 발음 스타일 통제 후 성능        |

---

# 5. Negative 클래스가 너무 약함

현재 negative는 “일반 문장”입니다. 그런데 PII 탐지에서 진짜 어려운 negative는 이런 것입니다.

```text
내 번호는 아니고 예시는 공일공 일이삼사 오육칠팔이야
회의실 번호는 301호입니다
주문번호는 20260613001입니다
비밀번호는 말하지 마세요
전화번호 형식처럼 들리지만 실제 PII가 아닌 숫자열
```

즉, 모델이 정말 유용하려면 **숫자는 있지만 PII는 아닌 음성**을 negative에 포함해야 합니다.

현재 negative가 숫자 거의 없는 일반 문장이라면, 모델은 사실상 다음 과제를 푸는 것입니다.

> “숫자 나열 음성인가 아닌가?”

이건 PII 탐지보다 훨씬 쉬운 문제입니다.

## 추가해야 할 hard negative

| 유형           | 예시                         |
| ------------ | -------------------------- |
| 숫자 포함 일반 문장  | “오늘은 2026년 6월 13일입니다.”     |
| 전화번호 비슷한 숫자열 | “010 1234 5678 형식은 예시입니다.” |
| 주문번호/우편번호/날짜 | “주문번호는 20260613001입니다.”    |
| 반복 숫자        | “하나 둘 셋 넷 다섯”              |
| 짧은 숫자열       | “3번 창구로 가세요.”              |

이 hard negative 없이 높은 성능이 나오면, 그 성능은 실사용 PII 탐지 성능으로 보기 어렵습니다.

# 6. Positive도 너무 단일함

Positive가 전화번호 하나라면, 모델이 배우는 것은 “PII”가 아니라 “전화번호 낭독 패턴”입니다.

이번 범위가 전화번호 PII라면 괜찮습니다. 다만 문서에서는 명확히 이렇게 써야 합니다.

> 본 실험의 PII는 일반적 개인정보 전체가 아니라, 전화번호 포함 여부에 한정한다.

현재는 “PII 포함 여부”라고 쓰여 있어서 범위가 넓어 보입니다. 실제로는 **phone-number detection from speech**에 가깝습니다.

따라서 제목도 더 정확히 쓰면 좋습니다.

```text
오디오 기반 전화번호 포함 여부 분류 실험
```

또는

```text
STT 없는 전화번호 PII 음성 프리필터 가능성 실험
```

# 7. ConvNeXt 비교의 의미가 애매함

Simple CNN과 ConvNeXt를 비교하는 것은 구현상 괜찮습니다. 하지만 실험 목적과는 약간 어긋날 수 있습니다.

이 실험의 핵심은 “STT 없는 경량 경로가 보조지표로 쓸 만한가”입니다. 그렇다면 ConvNeXt Tiny는 오히려 무거운 편입니다.

ConvNeXt Tiny는 약 28.6M params라고 적혀 있는데, 프리필터 목적이라면 다음 모델이 더 적절할 수 있습니다.

| 모델                | 이유                 |
| ----------------- | ------------------ |
| Simple CNN        | 경량 baseline        |
| MobileNetV3 Small | 모바일/실시간 프리필터에 더 적합 |
| EfficientNet-B0   | 작은 이미지 분류 baseline |
| ResNet18          | 고전 CNN baseline    |
| ConvNeXt Tiny     | 성능 상한 확인용          |

ConvNeXt를 쓰는 것은 나쁘지 않습니다. 다만 **프리필터 가치 검증**이라는 목표에는 `MobileNetV3`나 `EfficientNet-B0`가 더 자연스럽습니다.

지금 구조라면 ConvNeXt는 이렇게 포지셔닝하는 게 맞습니다.

> ConvNeXt는 경량 프리필터 후보라기보다는, 동일 입력에서 CNN 계열이 도달할 수 있는 성능 상한을 보는 비교군이다.

# 8. 효율성 지표는 좋지만, 기준이 더 필요함

모델 크기, latency, throughput, FLOPs를 기록하겠다는 점은 좋습니다. 다만 “그래서 어느 정도면 프리필터로 의미 있는가?”라는 판단 기준이 없습니다.

예를 들어 프리필터라면 다음 기준이 있어야 합니다.

| 항목                  | 필요한 기준                                     |
| ------------------- | ------------------------------------------ |
| Recall              | 높아야 함. PII를 놓치면 안 됨                        |
| Precision           | 낮아도 어느 정도 허용 가능                            |
| False Negative Rate | 핵심 지표                                      |
| STT 호출 절감률          | 프리필터의 실제 가치                                |
| End-to-end latency  | 멜 변환 포함해야 함                                |
| Threshold 조정        | F1 최대점이 아니라 high-recall operating point 필요 |

프리필터는 F1 최적화 모델이 아닙니다.
실제 목적은 보통 다음입니다.

```text
Recall 95% 이상을 유지하면서 STT 호출량을 얼마나 줄일 수 있는가?
```

따라서 F1만 보면 안 됩니다. PR curve, ROC curve, threshold별 recall/precision, STT-call reduction estimate가 필요합니다.

예시:

| Threshold | Recall | Precision | STT 호출 비율 | STT 절감률 |
| --------: | -----: | --------: | --------: | ------: |
|       0.2 |   0.98 |      0.55 |       72% |     28% |
|       0.5 |   0.91 |      0.78 |       54% |     46% |
|       0.8 |   0.70 |      0.90 |       35% |     65% |

이런 표가 있어야 “보조지표 가치”를 판단할 수 있습니다.

# 9. 실험 결론 문구는 더 엄격해야 함

현재 결론 구조는 좋습니다.

> (a) 정설 경로 대체 가능성
> (b) 경량 프리필터 가치

다만 현재 범위에서는 **(a)는 거의 판단 불가능**합니다.

왜냐하면 STT+NLP baseline을 범위 밖으로 뺐기 때문입니다. 그러면 “정설 경로를 대체할 만큼 통하는가”는 직접 판단할 수 없습니다.

가능한 결론은 이 정도입니다.

```text
본 실험은 STT 없는 멜 스펙트로그램 기반 CNN이
현재 합성 전화번호 데이터셋에서 positive/negative를 구분할 수 있는지를 검증했다.

다만 positive/negative 간 길이, 숫자 발화 방식, 문장 구조 차이가 존재하므로,
높은 성능이 곧 PII 의미 이해 또는 실사용 PII 탐지 가능성을 의미하지는 않는다.

따라서 본 결과는 정설 경로 대체 근거라기보다,
전화번호 낭독 패턴에 대한 경량 acoustic pre-filter 가능성의 초기 증거로 해석해야 한다.
```

이 정도로 낮춰야 정직합니다.

# 10. 현재 계획에서 좋은 점

비판할 부분이 많지만, 장점도 분명합니다.

## 장점

| 항목          | 평가                                                      |
| ----------- | ------------------------------------------------------- |
| 목표 정의       | “성능 향상”이 아니라 “작동 가능성 검증”으로 낮춘 점은 좋음                     |
| 범위 통제       | 모델 2개, 데이터 2000개, binary classification으로 현실적           |
| 전처리         | log-mel 기반 접근은 타당                                       |
| 동일 split 비교 | 모델 비교의 기본 공정성 확보                                        |
| 효율성 지표 포함   | 프리필터 가설과 잘 맞음                                           |
| 한계 인식       | 길이/발음 스타일 confound를 이미 문서에 적은 점은 좋음                     |
| 구현 구조       | `dataset.py`, `models/`, `train.py`, `infer.py` 구조는 깔끔함 |

특히 “중간 텍스트를 남기지 않는다”는 장점은 보안/프라이버시 관점에서 의미가 있습니다. 다만 멜 스펙트로그램도 완전히 비민감하다고 단정하면 안 됩니다. 원음 복원 가능성은 낮아도, 발화자의 음향 정보와 민감 발화 패턴이 남을 수 있습니다.

# 11. 우선순위별 수정 권고

## 반드시 해야 함

현재 실험 설계의 신뢰도를 올리려면 최소한 이것들은 넣는 게 좋습니다.

1. **Duration-only baseline 추가**

   * 길이만으로 분류가 되는지 확인
   * 이걸 안 하면 CNN 성능 해석이 위험함

2. **Length-matched evaluation 추가**

   * positive/negative 길이 분포를 맞춘 test subset 별도 평가

3. **Hard negative 추가**

   * 숫자는 있지만 PII가 아닌 음성
   * 전화번호 비슷하지만 실제 PII가 아닌 문장

4. **Speaker/template-disjoint split 검토**

   * 데이터 생성 방식이 템플릿/TTS 기반이면 거의 필수

5. **프리필터 기준을 F1이 아니라 recall 중심으로 재정의**

   * high recall threshold에서 STT 호출 절감률 산출

---

## 가능하면 해야 함

1. `00002` positive를 이번 범위 안으로 당기는 것

   * 발음 스타일 통제에 매우 중요함
   * “추후 과제”로 미루면 현재 실험의 설득력이 약함

2. MobileNetV3 또는 EfficientNet-B0 추가

   * 프리필터 목적이라면 ConvNeXt보다 더 타당한 비교군

3. PR curve / ROC-AUC 추가

   * threshold 기반 운용 가능성 판단에 필요

4. seed 3개 이상 반복 실험

   * 2000개 데이터는 split 운에 민감할 수 있음

5. 음성 증강 추가

   * noise, speed perturbation, volume jitter
   * 단, train에만 적용하고 test는 깨끗하게 유지

# 최종 판단

현재 계획은 **“CNN 파이프라인 구현 실험”으로는 충분히 좋습니다.**
하지만 **“STT 없는 PII 탐지 접근이 유효한가”를 검증하는 실험**으로는 아직 약합니다.

가장 냉정하게 말하면, 지금 설계 그대로 높은 F1이 나와도 제3자는 이렇게 반박할 수 있습니다.

> 이건 PII 탐지가 아니라 긴 숫자 나열 음성 탐지 아닌가?
> 길이 차이와 발화 스타일 차이만으로도 맞힐 수 있는 거 아닌가?
> 같은 TTS/템플릿이 train/test에 섞인 거 아닌가?
> hard negative가 없는데 실사용성이 있다고 볼 수 있나?

따라서 plan.md를 살리려면 결론을 낮추거나, 통제 실험을 추가해야 합니다.

가장 현실적인 수정 방향은 이겁니다.

```text
본 실험은 STT 없는 멜 스펙트로그램 기반 CNN이
전화번호 낭독 패턴을 경량으로 선별할 수 있는지 확인하는 초기 feasibility test이다.

PII 의미 이해나 정설 경로 대체 가능성은 본 실험만으로 주장하지 않는다.
대신 duration-only baseline, length-matched test, hard negative test를 통해
단순 artifact 의존 여부를 점검하고,
high-recall threshold에서 STT 호출 절감 가능성을 보조적으로 평가한다.
```

이렇게 바꾸면 훨씬 방어 가능한 실험 설계가 됩니다.
